# JOJOBI Backoffice — admin/ Documentation

A Laravel 12 (PHP 8.2) admin panel for JOJOBI_MART: multi-location POS, batch-level
inventory, orders/returns/exchanges, an AI ops assistant, and financial reporting —
gated end to end by a custom access-key permission layer.

Generated by reading `admin/` directly — `routes/web.php`, `app/Http/Controllers`,
`app/Models`, `app/Services`, `config/*.php`, and `.env` keys (values never read).
No other folder in the repository (`admin copy`, the zip archives) was consulted.

Stats: **30 controllers · 33 models · 6 services · ~250 gated routes · 21 permission domains**

## 2. Access Control Pipeline

Every route below (bar one) passes through the same two-stage gate before a controller
method runs. The permission system is homegrown — not Tyro's — built on a single pivot
table.

```
1. auth          → session must resolve to a logged-in User, else redirect to tyro-login.login
2. tyro.access    → TyroAccess::handle() reads the route's `access_key` default.
                    admin / super-admin roles bypass immediately.
3. AccessService  → canAccessKey() checks PrivilegeAccessKey rows (cached 1h per key),
                    matched by exact user, by role, or a global (null, null) grant.
4. outcome        → allow, or 403 (deny-by-default: allowIfNoMapping = false).
                    Denials are logged with user, key, route and URL.
```

Access keys are strings like `orders` or `ai_assistant`, defined once in
`App\Support\AccessKeys` so the mapping UI (`AccessKeyMappingController`), the grant
form (`PrivilegeController`), and the routes that consume them can't silently drift
apart.

`AiAssistantController` deliberately routes around this for its index/state pages so
an unprivileged user lands on a "request access" screen instead of a bare 403 — the
actual chat endpoints stay gated.

**Public exception:** `GET /order-status/{order}` (`PublicOrderController`) needs no
login — it's reached only via the **signed** URL baked into a receipt's QR code, and
Laravel's signature check rejects any tampered link.

### Point of Sale & Gifts

One active `Cart` per session, locked row-for-row against live `BatchStock` so two
tills can't oversell the same batch.

| access_key | Routes | Controller | Key actions |
|---|---|---|---|
| `pos` | 15 | `CartController` | `search`, `add`, `updateItem`, `removeItem`, `setCustomer`, `applyRewards`, `clearRewards`, `checkout`, `addManualGift`, `setLocation` |
| `gift_audit` | 4 | `ProductGiftController` | `index`, `export`, `updateStatus` |

`CartController` is the largest controller in the app: unit conversion between sale
units and a batch's base unit, reward-point redemption, and a checkout path that turns
the cart into an `Order`. Stock safety is enforced with per-request row locks
(`lockActiveCart`, `assertBatchStockAvailable`) so concurrent adds on the same
batch/location can't both succeed past available stock.

Free-gift line items aren't added by hand — they're computed by
`CartGiftService::sync()` every time the cart changes (see §4) and clamped to whatever
stock actually exists at the selected location.

### AI Assistant

A tool-calling chat agent wired directly to this app's own data and a handful of
write actions, gated per-user on top of the RBAC system above.

| access_key | Routes | Controller | Key actions |
|---|---|---|---|
| `ai_assistant` | 6 gated + 3 ungated | `AiAssistantController` | `index`/`state`/`requestAccess` reachable by any logged-in user; `chat`/`resolve`/`reset`/`updateModel`/`logs` stay gated |

**`GeminiAssistantService`** (`app/Services/AI`) owns the whole conversation loop:
builds the system instruction + tool declarations, calls Gemini, and if the model
requests a tool, executes it and feeds the result back — up to Gemini's own turn
limit — before returning the final reply. Per-user conversation history and any
pending confirmation live in the **session**, not the database.

Write-capable tools don't execute immediately: they return a confirmation prompt that
`resolvePending()` must approve before `dispatchToController()` actually calls into
the real controller — so the AI can propose a product or batch creation, but a human
clicks confirm.

Read-only tools: `getFinancialSummary`, `getTopSellingProducts`, `getProductSales`,
`listProducts`, `listCategories`, `listLocations`, `getTrendingProducts`,
`getCategoryPerformance`, `getLowStockProducts`, `getRestockRecommendations`,
`getPaymentSummary`, `searchOrders`, `getOrderDetails`, `searchCustomers`.

Write tools (require confirmation): `createProduct`, `createCategory`,
`createProductBatch`.

## 4. Support Services

Framework-agnostic classes several controllers share, so the business rules
underneath them live in one place instead of being copy-pasted per controller.

| Service | Responsibility |
|---|---|
| **`InventoryService`** | The single writer of stock movement. `post(StockTransaction $tx)` row-locks the affected `BatchStock` (`lockStockRow`), applies each transfer line (`applyTransferLine`), and appends an immutable `StockLedger` entry (`writeLedger`) — used by `StockTransferController`, `ReturnController` and validated request flows, so every stock-affecting action funnels through the same locked-write path. |
| **`CartGiftService`** | `sync(Cart $cart)` recomputes which free-gift line items a cart qualifies for, clamping quantity to stock at the cart's location (`clampGiftQtyByLocationStock`) and removing gifts no longer earned when the cart changes (`removeInvalidAutoGifts`). Also runnable via `php artisan cart:gifts-sync {cart_id}`. |
| **`RealtimeMetricsService`** | Per-location live counters — pending orders, low-stock count, abandoned carts — held in a single `RealtimeMetric` row, incremented in place. Fed by `OrderObserver` and `BatchStockObserver`; read by the dashboards' SSE `stream` endpoints. |
| **`AccessService`** | The RBAC gate (§2) — reused verbatim by `GeminiAssistantService::availableToolsFor()` so the AI can never offer a tool the same user couldn't reach through the UI. |
| **`TabularExporter`** (`app/Services/Report`) | Shared CSV/XLSX table builder behind every `export()`/`exportCsv()` action across expenses, gift audit, and reports/dashboard modules. |

## 5. Data Model

33 Eloquent models, grouped by business area with their direct relationships.

**Catalog**
- `Product` → category, brand, images*, statuses*, orderItems*
- `ProductBatch` → product, stocks*/batchStocks*, images* (through), freeProduct
- `BatchStock` → batch, location *(qty on hand per batch × location)*
- `Category` → parent, children* *(self-referencing tree)*
- `Brand`, `ProductImage`, `ProductStatus` → product

**Point of sale**
- `Cart` → items*, customer
- `CartItem` → batch, product, image, parent, gifts* *(self-ref for auto-gift lines)*

**Orders**
- `Order` → items*, customer, payments*, location, parentOrder, childOrders*, originalOrder
- `OrderItem` → order, productBatch, product
- `OrderSplit` → originalOrder, parentOrder, childOrder, createdBy
- `Payment` → order
- `Exchange` → lines*, order; `ExchangeLine` → exchange
- `ProductReturn` → items*, order; `ReturnItem` → parentReturn, batch

**Stock movement**
- `StockTransaction` → lines*, fromLocation, toLocation
- `StockTransactionLine` → tx, batch, product
- `StockLedger` — append-only, written by `InventoryService` only
- `Location` — referenced by nearly every model above

**Customers**
- `Customer` → balanceLedgers*, rewardLedgers*, orders*
- `CustomerBalance`, `CustomerRewardLedger` → customer *(append-only ledgers)*

**Identity & RBAC**
- `User` → kycDetail, privilegeAccessKeys*
- `PrivilegeAccessKey` → privilege†, role†, user *(the RBAC↔access_key bridge, §2)*
- `KycUser` → user
- † `Privilege` and `Role` are `HasinHayder\Tyro` package models, not local

**Finance**
- `Expense` → category, location, creator
- `ExpenseCategory` → expenses*

**AI & activity**
- `AiAssistantLog` → user *(every tool call, logged)*
- `AiAccessRequest` → user, resolvedBy
- `Timeline` → timelineable (morphTo, any model), causer *(the audit log in §3)*
- `RealtimeMetric`, `Setting` — singleton-per-location / key-value config

`Timeline` attaches to other models through a shared `HasTimeline` concern
(`app/Models/Concerns`) rather than being wired model-by-model — any model using the
trait gets an activity trail for free.

## 6. Appendix

**Middleware**
- `tyro.access` → `TyroAccess`, the gate used everywhere (§2).
- `AdminMiddleware` — a second, stricter admin/super-admin-only gate (JSON 403 on
  failure), present in the codebase but **not currently attached** to any route in
  `routes/web.php`.

**Observers**
- `OrderObserver` — on `created`/`updated`, bumps the pending-order and
  abandoned-cart counters in `RealtimeMetricsService`.
- `BatchStockObserver` — on `updated`, recalculates the low-stock counter for that
  batch's location.

**Console commands**
- `cart:gifts-sync {cart_id}` — re-runs `CartGiftService::sync()` for one cart
  outside the request cycle.
- `app:finance-snapshot` — precomputes the figures `FinancialDashboardController`
  would otherwise query live.

**Global helpers** (`app/Helpers/helpers.php`, autoloaded via `composer.json` "files")
`app_currency_symbol()`, `currency_bdt()`, `format_currency()`, `getContrastColor()`,
`is_sub_order()`, `is_parent_order()`, `get_order_type()`, `get_order_type_badge()`.

**Housekeeping notes**
- `routes/web.php` still imports `App\Http\Controllers\CartGiftAuditController`, a
  class that no longer exists in `app/Http/Controllers` — an unused, dead import
  (harmless in PHP, but worth deleting).
- `ManualGiftController` also exists as a file but is never referenced by any route;
  the live manual-gift endpoints are `CartController::addManualGift` /
  `OrderController::addManualGift` instead.
